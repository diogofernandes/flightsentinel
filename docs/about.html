What a recruiter should know

GitHub Pages serves the files; it does not run the backend. The complete live Python application is available in the source with deployment instructions.

FlightSentinel connects a Python backend, a machine-learning detector and a React dashboard into one working telemetry demonstrator. Its strongest contribution is the complete engineering pipeline and reproducible evaluation. It demonstrates backend development, asynchronous streaming, applied machine learning and interface design.

All readings are generated. This is a portfolio experiment, not avionics, a validated stall detector or software for operational flight decisions. The score measures unusualness, not the probability of an accident.

Isolation Forest measures unusualness.

03 · Confirm

Persistence stabilises alerts.

04 · Display

WebSockets deliver frames to React.

  1. Simulation: altitude, airspeed, pitch, roll, vertical speed and heading follow smooth signals with seeded noise. Altitude is integrated from vertical speed so the two agree. Every 30 simulation seconds, an eight-second combined deviation changes several channels. The dashboard repeats 120-second sessions. This is an illustrative generator, not an aircraft dynamics model.
  2. Detection: four inputs enter the model: airspeed, pitch, roll and vertical speed. Altitude and heading are display-only because an absolute altitude or direction alone does not establish abnormal behaviour. This simplified feature set is not validated for aviation use.
  3. Confirmation: three consecutive scores above the threshold confirm an event. Five below the threshold minus 0.03 clear it. The lower clearing threshold prevents rapid switching around the boundary. This logic smooths decisions; it does not teach the model flight sequences.
  4. Delivery: one server task generates and scores each frame once for all viewers. Each subscriber keeps only the newest queued frame, preventing a backlog for slow browsers. Another viewer does not speed up the simulation. The target is 10 Hz, without a hard real-time guarantee.
  5. Interface: React shows six readouts, four charts and confirmed events. The client rejects invalid or out-of-order frames, retries failed connections with increasing delays and marks stale readings unavailable. New sessions reset history. The browser event log is temporary, not a persistent audit trail.

The portfolio demo replays saved, model-scored synthetic output. It does not run browser inference. The full dashboard runs with the Python backend; the demo page includes its actual screenshot and setup instructions.

Why Isolation Forest?

Isolation Forest is an established unsupervised anomaly-detection algorithm. Random trees divide the input space; unusual observations tend to be isolated with fewer divisions than familiar observations. Combining the trees gives a relative unusualness score. Official algorithm documentation.

A practical starting point

It learns a reference envelope from normal examples without requiring labelled examples of every anomaly. It handles several numeric inputs together, runs on CPU and is straightforward to reproduce with scikit-learn. That makes it suitable for a small streaming experiment.

A choice to evaluate

It does not know aircraft limits or flight phases. This implementation scores individual frames without learned temporal context. A global score can miss a single-channel change, so the evaluation includes simple rules as a baseline.

The configuration uses 200 trees, random seed 42 and one model worker. Training happens at backend startup; this is not online learning. The tree count is a practical setting, not the result of a documented hyperparameter search. Neither the model nor the setting is claimed to be optimal.

Rules are easier to interpret when meaningful limits are known. Sequence models could examine change over time, but add complexity and still need credible data. Alternative models were not comprehensively benchmarked here. Isolation Forest is an engineering starting point, not a novel algorithm.

Training, calibration and testing

  1. Train: fit on 6,000 generated normal frames with seed 42.
  2. Calibrate: score 6,000 separate normal frames with seed 43. Their 99.5th percentile selects the threshold, approximately 0.5779.
  3. Test: evaluate combined, bank-only and airspeed-only deviations at full and half severity with seeds 101, 102 and 103. Test results do not select the threshold.

The code reverses scikit-learn's score direction so higher displayed values mean more unusual readings. A score of 0.60 does not mean a 60% chance of danger. The calibration percentile does not guarantee a 0.5% false-alert rate on new data.

All splits share the same generator and nominal envelope. Separate noise seeds test repeatability within a synthetic experiment, not generalisation to real aircraft.

Results, including the misses

Each scenario and severity combines three 299.9-second runs: 8,997 frames and 27 complete injected events. Event detection counts a confirmed alert during an injected interval. Frame recall counts individual injected frames exceeding the raw threshold. Those metrics answer different questions.

On 6,000 normal-only holdout frames, 0.45% crossed the raw threshold, with zero confirmed false-alert events. A finite run does not prove false alerts cannot occur. Median delays describe detected events only; missed events remain visible in the totals.

The illustrative rule baseline flags airspeed below 85 knots, absolute roll above 25 degrees, pitch above 8 degrees or vertical speed below −500 feet/minute. These are experiment thresholds, not aircraft operating limits.

The model catches the combined scenario; simple rules are stronger on the full-severity isolated scenarios. Half-severity results vary too. Combined changes are easier for this model to separate, while one changed feature can be insufficient to raise its global score. This does not show universal ML superiority.

There is no PyTorch model, GPU requirement, database, authentication, real telemetry ingestion or persistent event store. Run one server worker: each process owns a separate simulation.

Engineering value and next steps

The useful questions go beyond a model score: do several viewers receive a consistent stream, can the interface distinguish missing data from normal data, and can results be reproduced and compared with simpler alternatives? This project makes those questions visible and testable.

Its strongest portfolio evidence is Python/backend and full-stack engineering with an applied ML experiment. Flight phases, sensor faults, turbulence, aircraft-specific limits and performance on independent flights remain unvalidated.

The most valuable next step is recorded flight-log replay, with evaluation split by flight and flight phase. Further work should compare rules and models on those data, report false alerts per flight hour and missed events, and investigate why readings trigger a score. Changing the algorithm alone would not resolve the data limitation.
